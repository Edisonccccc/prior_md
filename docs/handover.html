PriorMD · handover

What was built, and what it would take to continue

development stopped · 13 Oct 2026

This page is for whoever owns the decision about what happens next. It assumes no technical background. It says what exists, what it is worth, what is missing, and the one thing that is blocking everything else.

1The idea, and whether it held up

A prior authorization is how an insurer is convinced to pay for an expensive therapy — here, home IV infusion delivered at a patient's house. A licensed specialist reads a referral from a doctor and produces three things: a one-line summary of exactly what is being requested with all its billing codes and quantities, the answers to the insurer's questionnaire, and the diagnosis code that justifies the whole request.

The bet behind this project was that most of that work is arithmetic, and only a small part is judgment. If that is true, software can do the arithmetic perfectly, leave the judgment to a human, and still save most of the time.

The bet held up. The arithmetic turned out to be exactly as mechanical as hoped — counting doses across a treatment period, rounding vials, converting to billing units, computing day supply — and all of it is now built and locked down by tests. The judgment part turned out to be roughly as hard as feared, and it is the part that was never built.

2Where it actually got to

The project tracked twelve checkpoints across three stages. Four are met.

4 of 12 checkpoints metstage 0 complete · stage 1 partial

Translated: the groundwork is finished and proven, and roughly a third of the product that would actually be useful to a specialist exists. The pipeline was designed as five stages, each handing off to the next.

1Read the referral Pull the drug, dose, frequency, dates, diagnosis and insurance out of the doctor's paperwork. written, never tested
2Distrust what was read Check every extracted value before anything is calculated from it. Anything unproven stops the line. built
3Do the arithmetic Doses, vials, billing units, day supply, and the final one-line request. No guessing anywhere. built & tested
4Make the judgment call Which diagnosis code to use, and whether this case will actually be approved. not built
5Specialist reviews and submits A person approves everything before it goes to the insurer. Deliberately last, and deliberately never removed. not built

Stage 1 is written but has never been run against a real referral, because no real referral was ever available. That is the blocker described in section 5.

3What you have that is worth keeping

Three things, in order of how hard they would be to recreate.

asset 1 · the hard-won one

A working calculation engine with the specialist's rules baked in

About 1,300 lines of code and 48 automated tests. The code itself is not the valuable part — a competent engineer could rewrite it in a week. The valuable part is that every rule in it came from the specialist directly, and every example she gave is now a permanent test. When she corrected something, the correction became a test that fails if anyone ever undoes it. That accumulated set of rulings — including two rounds of interviews and her written answers — is months of expert time, and it is the thing that would be genuinely painful to reconstruct.

asset 2

A written decision trail

Every significant design decision is recorded with the reasoning behind it and, crucially, what would overturn it. Four published documents cover the system design, a plain-language overview, the proposal shown to the specialist, and an assessment of what her latest answers changed. A planning board tracks the open questions, each with what is known, what is not, and who can decide it. Someone picking this up does not have to reverse-engineer intent from code.

asset 3 · not yours to keep

The specialist relationship and her case library

The specialist supplied 21 real solved cases covering 16 different medications, each with the insurer's response, plus written answers to two rounds of detailed questions. This material is the only source of ground truth the project ever had. It is her confidential data, it is deliberately not in the code repository, and section 7 covers what should happen to it.

4What is missing, stated plainly

The judgment layer — the part that decides whether a request gets approved

Choosing the right diagnosis code is not arithmetic. The specialist demonstrated this on the one fully worked case: she deliberately coded a post-surgical wound infection as a skin infection rather than a hardware infection, because the first route is clean under that patient's drug benefit and the second one invites a denial. Both codes were defensible from the chart. Only one gets paid. Nothing in the current system makes that kind of call.

The insurer's questionnaire — about a third of the deliverable, zero percent built

Every submission includes a payer questionnaire. Across the 21 cases we measured 186 questions, of which 98 were answered and 88 were left blank. Nothing in the system generates, checks or scores those answers. This is not a missing feature at the edge of the product — it is one of the three things a specialist produces, and it was never started.

Stage 1 has never been measured

The code that reads a referral exists, but there is no way to know how well it works, because we never had a real referral to run it on. See the next section.

One thing to be careful about if this restarts

The 21 cases are currently doing two jobs at once: they are the examples the system would learn from and the test set used to judge whether it works. That is circular — a system can score well simply by having memorised its own exam. Whoever restarts should split them, roughly 14 to learn from and 7 held back for testing, and commit to the split before looking at results. The honest caveat is that 7 held-back cases means the score moves in jumps of about 14 percentage points, so it detects disasters and not much else.

5The one thing blocking everything

No real referral packet was ever obtained. One would unblock more than anything else on this page.

The project asked for the original referrals behind the 21 cases twice. What arrived both times was the finished submission and the insurer's response, never the input document. On 13 October this was confirmed as all there is.

The specialist described what a referral contains: the physician's order, progress notes, hospital records, discharge notes, specialist notes, lab results, cultures, medication history, diagnosis, demographics and insurance — "sometimes one big PDF and sometimes several different documents", and on one case, "hundreds of pages long".

That description changes the problem. Reading a tidy two-page order is a parsing problem. Finding the right facts inside several hundred pages of mixed hospital records is a search problem, and it fails differently — it fails by missing something that was there, quietly, with no error message. The current code was written for the easy version and has never met the hard one.

A single real de-identified referral packet would be worth more to this project than another twenty solved cases. It would settle how the documents are actually shaped, how noisy they are, and how deep the information is buried, and it would turn one of the existing test cases from a partial check into a genuine end-to-end one. One. Not twenty-one.

6Three questions nobody can answer without the specialist

Each of these blocks real work, and each needs the specialist rather than an engineer.

questionwhy it is stuck
Can we get one real referral? Everything about stage 1 depends on it, and it is the cheapest of the three to resolve — one de-identified packet, from any case, would do.
How should the questionnaire's blanks be categorised? She distinguishes a question the form never asked, a question that was asked but does not apply to this patient, and a question that genuinely needs an answer the chart does not support. The design treats the first two as the same thing. With 88 of 186 questions blank, getting this wrong makes any measurement of the questionnaire meaningless.
How should the system look up a drug it has never seen? She does not want a fixed list of medications built in; she wants the drug researched when the case arrives, from sources like the FDA label and the manufacturer's information. This collides with the project's central safety rule, which is that the system never acts on anything it cannot prove. A billing code read off a web page is somebody's claim, not a verified fact, and there is currently no agreed way to let one through the gate. This is the one open question that touches the architecture rather than a feature.

7The confidential material

Read this before archiving anything

The specialist's source material is on the development machine and is deliberately excluded from the code repository — one rule in the repository's ignore file covers the whole folder, and that was verified before anything was published. The repository is public; this material is not in it, and it must not end up in it.

whatdetail
Her reference document The 12 rules the whole engine is built on, plus one fully worked case. That worked case contains real patient data.
Case library21 solved cases, 16 medications, 46 files, about 43 MB, de-identified under the HIPAA Safe Harbor standard.
Interview answersTwo rounds, including the questionnaire returned on 13 October. The October file still needs filing alongside the rest.
Known gapOne case's questionnaire screenshot still shows a portal header with a name on it. It was found and logged but never cleaned, and all 46 files were never re-scanned.

Recommendation. No agreement was ever put in place with an AI vendor permitting this material to be processed — that agreement would have been required before any real use, and the project never got that far. With development stopped, there is no remaining reason to hold a copy. The clean ending is to return the material to her, confirm she has it, and then delete the local copy. Nothing has been deleted; that is the owner's call, not an automated one.

8If someone picks this up

What a new engineer needs, in the order they need it.

  • Day one, read two files. AGENT.md in the repository is the full technical handoff — what exists, why, what is dangerous, and what is unfinished. The system design document explains the architecture and why each piece is shaped the way it is. Everything else can wait.
  • Run the tests first. Two commands, no setup, no accounts, no network. If 48 tests pass, the engine is intact and they can trust it while they read.
  • Do not grow the drug list. There is a small table of four medications in the code. It looks like the start of a list. It is not — it covers the test cases and nothing more, and the specialist explicitly does not want a built-in list. The comment above it says so.
  • Get access to the specialist, or do not start. She is the only source of truth for every rule in the system. Without her, a new engineer can maintain what exists but cannot correctly extend it.
  • Get one referral before writing any new code. Section 5 explains why. Starting stage 1 work without one means building against a guess for a second time.

10An honest closing assessment

This is a good idea that was being built carefully, and it stopped at an awkward point: past the hard thinking, short of the useful product. The groundwork is unusually solid for an unfinished project — the architecture is written down, the reasoning is preserved, the specialist's rules are encoded and tested, and the things that are missing are known and named rather than discovered later by someone else.

What it never got was contact with reality. Not one real referral went through it, and no specialist ever used its output to submit an actual authorization. Until that happens, the confidence in it rests on expert interviews and internal consistency, not evidence. That is the honest line to give anyone who asks how far along it was.

If it restarts, the order is not negotiable: get one referral, settle the drug-lookup question with the specialist, then build the judgment layer. Doing those out of order wastes the groundwork that is already there.
